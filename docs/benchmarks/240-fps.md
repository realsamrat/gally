# 240 fps hill climb

Goal: the library benchmark holds 240 fps while the library moves (pinching through every level and
flick-scrolling), measured on the deployed playground.

These rounds were measured when the playground's library demo had an app header, tabs and a photo
viewer around the grid. The playground now shows the grid alone, so new runs aren't exactly
comparable with the numbers below.

### The trace check

`npm run bench:trace` runs a local production build twice with the probe, then twice with the probe
off (`?probe=0`) under a Chrome trace, and takes the main thread's busy time from the trace's
top-level tasks in 8.33 ms windows. Each check is saved to `.bench/trace-checks.jsonl` with its run
ids, build and trace files. p95 frame work, in ms (240 fps is 4.17 ms):

| `09075ae+42e2381`, 1440×900 | 2.0 · 2.2 | **3.4 · 3.6** | 25 of 617 · 24 of 618 | 3.9 · 4.1 | 6.6 · 5.3 | 2.5 · 2.5 |
| `09075ae+42e2381`, 1672×1166 | 3.0 · 3.0 | **4.5 · 4.3** | 38 of 621 · 34 of 617 | 5.4 · 4.0 | 7.0 · 6.7 | 3.5 · 3.3 |

The two measures differ in method: the probe misses gaps under 0.15 ms and runs in the same
session it measures; the trace adds tracing's own cost to every task and counts work in fixed
8.33 ms windows rather than the browser's frames. Neither is exact, and the trace consistently
reads higher. Both put the final build inside the target at 1440×900 and the original engine
well outside it; at 1672×1166 they disagree. With the probe off, the original engine's tiles are
about 1% blank instead of 69%: its background bitmap work runs during motion, and the trace counts
it. Earlier checks, on builds `09075ae+55d8ff3` and `09075ae+cfc6dfa` (r10), gave the same
picture; the original engine's trace files are kept in `.bench/baseline-engine/`.

## The measure

A browser can't show more frames than the display refreshes (120 Hz here), and Chrome's uncapped
mode (`--disable-frame-rate-limit --disable-gpu-vsync`) runs at 41–49 fps on this machine even on
an empty page, so no frame counter here can show 240 fps.

The benchmark measures **frame capacity** instead (`sampleFrames` in `playground/bench/run.ts`):
while pinching and flicking, a chain of message tasks runs whenever the main thread is free, and
any gap between two of them is counted as work. Each frame's work gives `1000 / work`, the frame
rate the main thread could sustain at that frame; a frame fits 240 fps at 4.17 ms or less.

**Target: p95 capacity while moving ≥ 240 fps** (at most 5% of frames over 4.17 ms) in each of
three runs on the deployed site. Work is counted per displayed frame (8.3 ms at 120 Hz), so
background work such as image loading counts in full in every frame it touches.

It is a proxy, with these limits:

- It measures the main thread only. Scrolling and the zoom transitions run on the compositor and
  GPU; their throughput isn't measured.
- Gaps under 0.15 ms are missed (timers here have 0.1 ms resolution), so many tiny tasks are
  undercounted; the trace check shows it reads lower than a trace. Anything else that keeps the
  thread from running a normal-priority task, including the operating system descheduling it, is
  counted as work.
- Each run first measures one second with nothing moving (`capacity.idle`). Images may still be
  loading then, so it is not a pure floor: p95 of 3–4.5 ms of work per frame for the original
  engine, about 1 ms for the final one.

### Two flaws found in review

Both were fixed before r8; earlier rounds were measured with them.

1. **It starved background work.** A continuously queued normal-priority task keeps
   background-priority tasks waiting while it runs. Gally's bitmap and image-element work ran at
   background priority, so it waited up to 2.6 s, until motion stopped, and was never counted.
   Gally now runs that work at user-visible priority (it is for tiles on screen). The original
   engine still uses background priority, so the probe still holds its work back.
2. **Its own garbage was counted.** It ran about 3,000 tasks per frame, and the messages' garbage
   (about half of all allocation during a pinch) brought major collections into the frames it
   measured. Each probe task now holds the thread for 0.1 ms before yielding; a task that becomes
   ready meanwhile runs right after and is counted in the next gap, so no work is hidden.

## How to run it

```bash
# The deployed site, as in the results (runs are saved there; the harness fails if a save fails)
npm run bench:fps -- --url https://gally-playground.vercel.app --headed --label <round>
npm run bench:fps -- --url https://gally-playground.vercel.app --headed --width 1672 --height 1166 --label <round>
# A local production build (saved to .bench/runs.jsonl)
npm run bench:fps -- --headed
# The probe against a trace, locally
npm run bench:trace
# Regression checks for the canvas renderer and loader readiness
npm run check:renderer
```

Each run is saved with `config.build` (the commit plus a hash of uncommitted changes, new files
included, to the engine, playground and build config; not to `scripts/` or `playground/functions/`) and
`config.label`; the harness keeps a receipt in `.bench/receipts.jsonl`. Headless
Chrome runs at 60 Hz, so it counts twice the work per frame.

The original engine (`09075ae-engine`) is the engine source from commit 09075ae with this branch's
playground, benchmark and scripts: export 09075ae (`git archive 09075ae`), copy `playground/`,
`scripts/`, `vite.config.ts` and `package.json` over it, set the `__GALLY_BUILD__` define in
`vite.config.ts` to `'09075ae-engine'`, and deploy it with `npm run deploy:playground -- --prod`.

Setup for the results: MacBook Pro M1 Max, 120 Hz display, load average 9–15 from other apps;
Chrome 156 through the harness (`--headed`); ego lite (Chromium) through its own automation at its
window size, stored with browser "Chrome" (its label tells them apart); images from the benchmark
fixtures on the Vercel CDN.

## What changed, and why

Traces of the original engine showed its own JavaScript was small; frames filled with the image
pipeline's main-thread work. Pinching through the dense levels finishes about 1,000 image loads in
2.6 s, and each cost several small tasks: fetch, `blob()`, a synchronous `createObjectURL` call
into the browser, decode, and cache eviction that re-sorted the whole cache. Reading a blob for
`createImageBitmap` on the main thread added a stream of small tasks per image. After that came
canvas drawing and React renders whose cost grew with the tiles on screen rather than with what
changed.

- **Image loader** (`src/image-loader.ts`, `src/image-fetcher.ts`): blob mode fetches, decodes,
  makes object URLs and resizes bitmaps in a worker, posting results in batches, with a
  main-thread fallback. Small images keep the bitmap they were decoded into, so canvas tiles fill
  as soon as an image loads. Image elements are made only for tiles that ask
  (`prepareElements`, `isRenderable`). Listeners hear which images changed.
- **Canvas renderer** (`src/renderers/library-canvas-renderer.ts`): a per-frame budget for first
  draws of new images, which the browser copies on the main thread; redraws of only the tiles
  whose images arrived; bands track whether they need a full pass and resume where one stopped;
  follow-up passes run within a time budget; a level change draws its canvas over the next frames
  while the outgoing snapshot covers it.
- **`GallyLibrary`**: no React render per image on canvas levels, or per scroll event within the
  rendered rows; DOM tiles show an image once it has decoded, so painting never decodes in the
  frame.

## What's left

- **Pinching alone** reaches 240 by the probe at 1440×900 but not by the trace (151–188 fps), and
  not at 1672×1166 by either.
- **1672×1166** meets the target by the probe but lands just over the line by the trace.
- **Single long frames:** the worst pinch frame is up to about 25 ms (p99 while moving is
  124–159 fps). They are level changes back into the DOM levels, where React renders a few hundred
  tiles and the browser lays them out.
- Next steps: render a DOM level's tiles over two frames, and measure on a quieter machine to
  separate CPU contention from Gally's work.
